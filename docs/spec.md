# FDE Project 1: Support Agent (flagship)

Spec v1, 2026-11-09. Part of [FDE Portfolio] (vault: `Projects/In progress/FDE Portfolio`).

## Goal
A support agent for a fictional company, built and measured the way an FDE would ship it to a real customer: it answers from the company's docs with citations, takes actions through tools, hands off to a human when unsure, and comes with an eval report and a runbook.

## The customer (fictional, disclosed as simulated)
- **Larkfield Coffee Co.**, an Indian D2C brand selling home coffee gear (grinders, brewers, beans) online.
- Synthetic data I write: 40 help-centre articles (shipping, returns, warranty, care, payments, subscriptions), 200 orders, 50 products with stock, 30 past tickets.
- Planted traps: two articles that contradict each other (old vs new return window), one with a prompt-injection line, policy edge cases.

## What it does
| Capability | Detail |
|---|---|
| Answer questions | Hybrid search (keyword + vector) over the help centre; every answer cites article and section |
| Tools | `lookup_order`, `check_stock`, `search_products`, `start_return`, `create_ticket` (audit 2026-11-10: `search_products` was added during the build; spec now matches the code) |
| Human in the loop | `start_return` and `create_ticket` need the user to confirm before they run |
| Hand-off | Unsure, out of scope, or angry customer: escalates to a ticket with a summary |
| Never | Invents order data, prices, dates or policy; follows instructions found inside documents |

## Channels
- REST API (FastAPI): `POST /chat`, `GET /health`, `GET /metrics`.
- Simple local web chat page for demos.
- Slack bot via Socket Mode (works locally, no public URL). Optional: needs a free Slack workspace.

## Stack (local only)
| Part | Choice |
|---|---|
| Language | Python 3.13, FastAPI, pytest |
| Database | Postgres + pgvector in Docker (docs, chunks, embeddings, orders, tickets, logs) |
| LLM | Ollama `fusion27b:iq3` default via `/api/chat` with tool calling; switch to a paid API by env var |
| Embeddings | Ollama `nomic-embed-text` (new, about 270 MB) |
| Run | `docker compose up` brings up DB + API; Ollama runs on the host |
| CI | GitHub Actions: lint + unit tests with a mocked LLM (CI can't run the 27B model) |

## Measuring it (the part that sells it)
- **Eval set, 60 cases:** 35 answerable questions, 15 tool tasks, 10 that must refuse or escalate (incl. the injection and contradiction traps).
- **Metrics:** answer correctness, citation correctness, tool-call correctness, correct refusals, p50/p95 latency, tokens per query, cost per query (local = Rs 0; paid API = actual).
- **Baselines:** (a) same LLM with no retrieval, (b) keyword-only retrieval. The agent ships only if it beats both, reported per category.
- **Scoring:** exact checks where possible (order fields, tool args); LLM-judge for free text, with 15 cases hand-checked to confirm the judge.

## Guardrails and operations
- Phone numbers and emails masked in logs.
- Structured JSON logs per request (retrieved chunks, tool calls, latency, tokens).
- Timeouts and retries on the LLM call; graceful "I'll pass this to a person" on failure.

## Done means
- From a clean clone: `docker compose up` + one ingest command works.
- Eval script runs the 60 cases and writes the report; README numbers match it.
- Unit tests and CI green. (audit 2026-11-10: there is no GitHub repo and no push, so "CI green" means the workflow file exists and its exact steps (ruff, pytest) pass locally; the README claims no CI badge until the repo is pushed.)
- Every trap case handled or honestly reported as a miss.
- (audit 2026-11-10) The LLM judge is validated: 15 answer cases hand-checked against the judge verdicts, agreement (x/15) and disagreements written in `docs/engagement.md`. Needed because the engagement calls the judge column "the better read"; no GPU required, use existing results files.
